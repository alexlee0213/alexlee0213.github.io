## 결론부터

**`100.64.0.0/10` 대역에 ping이 성공하는 것은 테일넷이 살아 있다는 증거가 아니다.**

이 대역은 Tailscale 전용이 아니라 RFC 6598이 정의한 **Shared Address Space**다. 통신사가 CGNAT에 쓰는 바로 그 대역이라, 테일넷이 죽어도 ISP망의 다른 장비가 같은 IP에 응답할 수 있다.

| 판별 지표 | 진짜 테일넷 피어 | ISP 쪽 가짜 응답 |
|---|---|---|
| ping TTL | `64` | `56` (실측) |
| `nc -z <ip> 22`/`443` | OPEN | CLOSED/FILTERED |
| `ifconfig \| grep "inet 100\."` | 자기 테일넷 IP 있음 | 없음 |
| `netstat -rn \| grep ^100` | 라우트 있음 | 없음 |
| 실제 서비스 응답 | 200 | timeout |

**가장 확실한 건 마지막 줄이다.** ICMP는 판단 근거로 너무 약하다.

## 무슨 일이 있었나

[Tailscale 이중 설치를 정리하는 중](/dev/2026/08/30/tailscale-완전-삭제-후-재설치-순서를-틀리면-재부팅을-헛쓴다/)이었다. Homebrew판 `tailscaled`를 중지하고 GUI 앱에 터널을 넘기는 단계였다.

Homebrew 데몬을 걷어내기 전 상태는 이랬다.

```
$ ping -c 2 100.101.102.103
64 bytes from 100.101.102.103: icmp_seq=0 time=184.3 ms
64 bytes from 100.101.102.103: icmp_seq=1 time=183.7 ms
```

제거 직후 다시 재보니 이렇게 나왔다.

```
$ ping -c 3 100.101.102.103
3 packets transmitted, 3 packets received, 0.0% packet loss
round-trip min/avg/max = 8.726/21.290/42.134 ms
```

**184ms에서 21ms로, 8배 빨라졌다.**

나는 이렇게 해석했다.

> Homebrew 데몬은 DERP 릴레이를 경유하고 있었고, 앱이 인수하면서 직접 연결(direct WireGuard path)을 뚫었다. 앱은 이미 로그인돼 있었고 그동안 소켓을 뺏겨 놀고 있었던 것이다.

그럴듯했다. 릴레이 경유가 직접 연결로 바뀌면 실제로 지연이 크게 준다. 심지어 "재로그인 단계를 건너뛰어도 되겠다"는 결론까지 냈다.

**전부 틀렸다.**

## 어디서 어긋났나

다음 단계에서 인터페이스를 확인하다 이상한 걸 봤다.

```
$ ifconfig | grep "inet 100\."
(출력 없음)

$ netstat -rn -f inet | grep "^100"
(출력 없음)
```

**이 맥에 테일넷 IP가 없다.** 100.64/10으로 가는 라우트도 없다. 그런데 ping은 된다.

오버레이 네트워크에 주소도 라우트도 없이 통신이 될 리 없다. 여기서 ping을 의심했어야 했다는 걸 깨달았다.

결정적 테스트를 돌렸다.

```
$ curl -sS -m 15 https://linux-server.tailnet-example.ts.net/health
curl: (28) Connection timed out after 15004 milliseconds

$ nc -z -G 5 100.101.102.103 443 ; echo $?
1                                    # CLOSED/FILTERED

$ nc -z -G 5 100.101.102.103 22 ; echo $?
1                                    # CLOSED/FILTERED

$ ping -c 2 100.101.102.103 | grep "bytes from"
64 bytes from 100.101.102.103: icmp_seq=0 ttl=56 time=7.511 ms
64 bytes from 100.101.102.103: icmp_seq=1 ttl=56 time=14.884 ms
```

**TTL이 56이다.**

---

## TTL이 결정적인 이유

리눅스는 기본 TTL을 64로 내보낸다. 이 값은 라우터를 하나 지날 때마다 1씩 줄어든다.

- **TTL 64로 도착** → 중간 IP 라우터를 거의 안 거쳤다는 뜻. 터널 안에서 캡슐화돼 왔으므로 내부 홉이 없다. 진짜 테일넷 피어다.
- **TTL 56으로 도착** → 8홉을 거쳤다는 뜻. 일반 인터넷 라우팅을 탄 것이다. 오버레이가 아니다.

지연 시간도 다시 보면 앞뒤가 안 맞았다. 정리 완료 후 진짜 테일넷이 복구됐을 때 측정값은 이랬다.

```
64 bytes from 100.101.102.103: icmp_seq=0 ttl=64 time=180.503 ms
```

**진짜 경로는 180ms고 가짜가 8ms였다.** 지연이 줄어든 게 아니라, 훨씬 가까운 엉뚱한 장비가 대신 답한 것이다. 나는 이 숫자를 개선의 증거로 읽었다. 정확히 거꾸로였다.

## 왜 이런 일이 생기나

`100.64.0.0/10`은 RFC 6598이 정의한 **Shared Address Space**다. 통신사가 가입자에게 공인 IP를 다 못 주는 상황에서 CGNAT용으로 쓰라고 별도로 떼어놓은 대역이다.

Tailscale은 이 대역을 테일넷 내부 주소로 쓴다. 사설 대역(`10/8`, `192.168/16`, `172.16/12`)과 충돌할 확률이 낮기 때문이다. 합리적인 선택이지만 **부작용이 하나 있다.**

터널이 죽으면 `100.x.x.x`로 가는 패킷이 오버레이가 아니라 **기본 게이트웨이로 나간다.** 그리고 사용자가 CGNAT을 쓰는 ISP에 있다면, 그 대역은 ISP 내부에서 실제로 라우팅되는 주소다. 운 나쁘면 같은 주소를 가진 다른 장비가 ICMP에 응답한다.

즉 **"응답이 온다"와 "내가 의도한 상대가 응답했다"는 전혀 다른 명제다.**

---

## 일반화

이건 Tailscale만의 문제가 아니다. 겹치는 주소 공간을 쓰는 모든 오버레이에 해당한다. WireGuard를 직접 굴리든, ZeroTier를 쓰든, 사내 VPN이 사설 대역을 쓰든 마찬가지다.

원격 서비스가 안 붙을 때의 진단 순서는 이렇게 잡는 게 낫다.

```bash
# 1. 오버레이 자체가 서 있는가 (가장 먼저)
ifconfig | grep "inet 100\."
netstat -rn -f inet | grep "^100"

# 2. 목표 포트가 열려 있는가 (살아있는 다른 포트와 대조)
nc -z -G 5 <ip> 22
nc -z -G 5 <ip> <목표포트>

# 3. 실제 서비스가 응답하는가 (최종 판정)
curl -sS -m 10 -w "%{http_code}\n" https://<host>/health

# 4. ping을 쓴다면 반드시 TTL까지 본다
ping -c 2 <ip> | grep "bytes from"
```

**ping은 1번이 통과한 뒤의 보조 지표로만 쓴다.** ping 하나로 터널 생사를 판정하지 않는다.

포트 대조에는 요령이 하나 있다. 같은 호스트의 **알려진 정상 포트를 대조군으로** 같이 때려보는 것이다. 22번이 열리고 목표 포트만 막히면 방화벽이나 리스너 바인딩 문제로 좁혀지고, 둘 다 막히면 경로 자체가 죽은 것이다.

거부 방식도 정보를 준다. **즉시 거부(RST)면 경로는 살아 있고 리스너가 없는 것**이고, **타임아웃이면 필터링이나 no-route**를 의심한다.

## 남은 교훈

이번에 내가 한 실수는 기술적 오류라기보다 추론의 문제였다.

숫자가 좋은 방향으로 움직였고(184ms → 8ms), 그 방향을 설명하는 그럴듯한 메커니즘이 있었다(릴레이 → 직접 연결). 그래서 검증 없이 받아들였다. **가설을 지지하는 증거가 나왔을 때가 가장 위험한 순간이다.**

되짚어보면 반증 비용은 명령어 하나였다. `ping`에 `grep "bytes from"`을 붙여 TTL을 보는 것, 혹은 `nc -z`로 포트를 한 번 확인하는 것. 몇 초면 끝났을 일이다.

> 성능이 예상보다 크게 개선됐을 때는, 개선을 설명하려 들기 전에 **측정 대상이 바뀌지 않았는지** 먼저 확인하자.

## 체크리스트

- [ ] `100.x` ping 성공을 터널 생존 증거로 쓰지 않기
- [ ] ping을 쓸 거면 TTL까지 확인 (`64` 대 `56`)
- [ ] 오버레이 인터페이스 주소와 라우트를 먼저 확인
- [ ] 목표 포트와 알려진 정상 포트를 대조
- [ ] 최종 판정은 실제 서비스 응답으로
- [ ] 지연이 급격히 개선됐으면 측정 대상 변경을 의심
