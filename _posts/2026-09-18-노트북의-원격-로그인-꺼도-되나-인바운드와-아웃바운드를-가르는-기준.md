## 결론부터

**"원격 로그인"은 서버 데몬(`sshd`) 스위치다. 들어오는 것만 막고, 나가는 것은 하나도 막지 않는다.**

| 기능 | sshd 끄면 |
|---|---|
| 다른 서버로 `ssh` 접속 | **영향 없음** |
| VS Code·Cursor의 Remote-SSH로 서버에 붙기 | **영향 없음** |
| `git push`, `scp`로 내보내기 | **영향 없음** |
| `LocalForward`/`ssh -R` 터널 | **영향 없음** |
| 외부에서 이 기계로 들어오기 | 차단 |
| 이 기계로 `scp`/`rsync` 당겨가기 | 차단 |
| **이 기계 자신에게 `ssh localhost`** | 차단 |

혼동은 거의 전부 "SSH를 끈다"는 표현에서 온다. 클라이언트(`ssh`)와 서버(`sshd`)는 별개 프로그램이고, 끄는 건 후자뿐이다.

다만 끄기 전에 확인할 것이 있다.

```bash
# 이 기계의 인바운드 경로가 SSH 말고 또 있는가
launchctl print-disabled system | grep -iE 'screensharing|openssh'
tailscale debug prefs | grep -i RunSSH
netstat -an -p tcp | awk '/LISTEN/ {print $4}' | sort -u
```

## 질문의 출발점

[1편](/dev/2026/09/18/평문-ssh-키-하나가-맥과-github을-동시에-열고-있었다/)에서 노출된 키를 정리하고 나니 `authorized_keys`가 비었다. 그러면 남은 질문은 이것이다. **이 노트북이 애초에 SSH 접속을 받아야 할 이유가 있나?**

"켜두면 언젠가 쓸모 있겠지"는 근거가 아니다. 끄면 구체적으로 무엇이 불편해지는지를 알아야 판단할 수 있다.

---

## 실측 1: 인바운드 경로가 SSH뿐인가

가장 중요한 건 **다른 길이 있는지**다. SSH가 유일한 진입로라면, 끄는 순간 원격 복구 수단이 0이 된다.

```bash
# 화면 공유(VNC)
$ launchctl print-disabled system | grep -i screensharing
	"com.apple.screensharing" => disabled

# Tailscale SSH 서버 기능
$ tailscale debug prefs | grep -i RunSSH
	"RunSSH": false,

# 실제 리스닝 포트
$ netstat -an -p tcp | awk '/LISTEN/ {print $4}' | sort -u
*.22
127.0.0.1.5901      # 다른 서버로 나가는 VNC 터널의 로컬 끝단 (인바운드 아님)
```

**SSH 하나뿐이었다.** 화면 공유는 꺼져 있고, Tailscale SSH도 비활성이다. 5901은 이 기계가 *나가서* 만든 터널의 로컬 끝이지 외부에서 들어오는 문이 아니다.

여기서 나온 결론은 "끄면 안 된다"가 아니라 **"끄면 원격으로 다시 켤 방법이 없다"**는 제약의 확인이다. 켜는 명령 자체가 SSH를 타야 하기 때문이다.

---

## 실측 2: 실제로 쓰고 있었나

```bash
# 최근 로그인 기록 (원격 접속은 호스트 정보가 함께 남는다)
$ last | grep -vE 'reboot|shutdown' | head

# 다른 기계들이 이 노트북을 SSH 대상으로 잡고 있는지
$ for h in server-a server-b; do
    ssh "$h" 'grep -il "my-laptop" ~/.ssh/config ~/.ssh/known_hosts 2>/dev/null; crontab -l 2>/dev/null | grep -i my-laptop'
  done
```

결과는 "`known_hosts`에 흔적은 있으나 상시 사용하는 설정·크론잡은 없음"이었다. 과거에 몇 번 들어온 적은 있지만 **자동화가 의존하고 있지는 않다**는 뜻이다.

## 오진: authorized_keys를 비웠으니 안전하다

키를 다 지웠으니 이제 아무도 못 들어온다고 생각하기 쉽다. 그런데 접속을 시도해보면 서버가 이렇게 답한다.

```
user@my-laptop: Permission denied (publickey,password,keyboard-interactive).
```

괄호 안을 봐야 한다. **`password`와 `keyboard-interactive`가 살아 있다.** macOS의 `sshd_config`는 거의 전부 주석 처리돼 있고, `PasswordAuthentication`의 OpenSSH 기본값은 `yes`다.

```bash
$ grep -vE '^\s*#|^\s*$' /etc/ssh/sshd_config
Include /etc/ssh/sshd_config.d/*
AuthorizedKeysFile	.ssh/authorized_keys
Subsystem	sftp	/usr/libexec/sftp-server
```

즉 **계정 암호만 알면 로그인이 가능한 상태**가 그대로 남아 있었다. 접근 대상은 `com.apple.access_ssh` 그룹으로 제한되는데, 기본 구성에서 여기에 admin 그룹이 들어간다.

```bash
$ dscl . -read /Groups/com.apple.access_ssh
NestedGroups: ABCDEFAB-CDEF-ABCD-EFAB-CDEF00000050   # admin 그룹
```

**키를 지우는 것과 문을 닫는 것은 다른 일이다.**

## 노트북이라는 조건이 판단을 뒤집는다

여기까지는 데스크톱에도 해당하는 이야기다. 그런데 이 기계는 노트북이고, 항상 들고 다닌다. 이 조건은 양쪽 저울을 **동시에** 기울인다.

- **위험은 커진다.** 리스닝 주소가 `*.22`, 즉 모든 인터페이스다. 카페·회사·공항 같은 신뢰할 수 없는 망에 붙을 때마다 같은 LAN의 누구에게나 암호 인증 창구가 열린다. 집에 고정된 기계보다 노출 빈도가 훨씬 높다.
- **끄는 비용은 작아진다.** 원격 복구가 필요한 상황(집에 두고 나왔는데 접속해야 함) 자체가 거의 없고, 기계가 늘 손에 있으니 다시 켜는 것도 명령 한 줄이다.

"집에 있는 서버라면 켜두고 잠그기, 들고 다니는 노트북이면 끄기"가 합리적인 갈림길이다.

## 끄기

```bash
sudo systemsetup -f -setremotelogin off
```

`-f`는 확인 프롬프트를 건너뛴다. 되돌릴 땐 `off`를 `on`으로. GUI로는 시스템 설정 → 일반 → 공유 → 원격 로그인.

> **주의**: 이 명령은 tty가 필요하다. 터미널 앱에서 직접 실행해야 하고, tty 없는 래퍼를 통하면 `sudo: a terminal is required to read the password`로 실패한다.

### 검증

```bash
# 1. 데몬 상태
$ launchctl print-disabled system | grep -i com.openssh.sshd
	"com.openssh.sshd" => disabled

# 2. 리스닝 포트 (LISTEN 줄이 사라져야 한다)
$ netstat -an -p tcp | grep -E '\.22 '

# 3. 실제 접속 시도 — 메시지 변화가 핵심
$ ssh -o ConnectTimeout=8 user@my-laptop 'echo IN'
ssh: connect to host my-laptop port 22: Connection refused
```

**`Permission denied`에서 `Connection refused`로 바뀐 것이 핵심이다.** 전자는 "문은 있는데 열쇠가 안 맞는다", 후자는 "문 자체가 없다"는 뜻이다.

### 함정: 기존 세션은 안 끊긴다

데몬을 꺼도 **이미 맺어진 연결은 그대로 살아 있다.** 실제로 확인해보니 몇 시간 전에 붙은 세션 하나가 계속 연결돼 있었다.

```bash
$ lsof -nP -iTCP@100.101.102.103:22
COMMAND     PID   USER  ...  TCP 100.101.102.103:22->100.101.102.104:42858 (ESTABLISHED)
```

접속 측에서 해당 클라이언트 프로세스를 종료해야 정리된다. **"껐으니 끝"이 아니라 남은 세션까지 확인해야 실제로 닫힌 것이다.**

---

## 끄지 않는다면: 잠그는 구성

원격 로그인이 계속 필요하다면 최소한 이 둘은 해야 한다.

```bash
sudo tee /etc/ssh/sshd_config.d/200-lockdown.conf <<'EOF'
ListenAddress 100.101.102.103        # VPN 인터페이스 주소만
PasswordAuthentication no
KbdInteractiveAuthentication no
EOF
sudo launchctl kickstart -k system/com.openssh.sshd
```

이러면 ① VPN 밖(LAN·인터넷)에서는 포트가 아예 안 보이고 ② 암호 무차별 대입이 불가능해진다. 그 상태에서 **본인이 통제하는 기계의 공개키 하나만** 복구용으로 등록해두면 안전과 복구 경로를 둘 다 갖는다.

그리고 공유기에 22번 포트포워딩이 걸려 있는지는 기계 안에서 확인할 수 없다. 걸려 있으면 인터넷 전체 노출이므로 따로 봐야 한다.

## 끄고 나면 실제로 불편해지는 것

정직하게 정리하면 이렇다.

1. **원격 복구 수단이 0** — 밖에서 이 기계에 들어갈 방법이 없고, 원격으로 다시 켤 수도 없다.
2. **다른 기계에서 이 기계로 당겨가기** — `scp`/`rsync` pull, 이 기계를 대상으로 한 Remote-SSH.
3. **외부에서 이 기계의 CLI를 호출하는 구조** — 서버에서 노트북의 명령을 실행하게 하는 브리지 같은 것.

3번이 필요해지면 인바운드를 다시 여는 대신 **역방향 터널**(노트북이 나가서 소켓만 여는 방식)을 쓰면 된다. 원격 로그인이 꺼진 상태에서도 동작하고, 상대 기계에 자격증명을 두지 않아도 된다.

## 체크리스트

- [ ] 인바운드 경로가 SSH뿐인지 확인 (화면 공유, VPN의 SSH 기능, 리스닝 포트)
- [ ] `last`와 다른 기계의 설정·크론잡으로 실제 사용 여부 확인
- [ ] `authorized_keys`를 비워도 **패스워드 인증은 살아 있다**는 것 인지
- [ ] 리스닝 주소가 `*`인지 특정 인터페이스인지 확인
- [ ] 끈 뒤 `Connection refused`로 바뀌는지 검증
- [ ] **기존 세션이 남아 있지 않은지** 확인
- [ ] 계속 켜둔다면 `ListenAddress` + `PasswordAuthentication no`는 최소 조건
