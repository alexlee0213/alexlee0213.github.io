## 한 줄 답

**이름은 아는데 DNS가 그 이름을 못 풀고, IP는 이미 알고 있을 때 임시로 넘기는 용도다.**

`/etc/hosts`는 `getaddrinfo()`가 DNS 질의보다 **먼저** 참조하는 정적 매핑표다. 그래서 DNS 계층 전체를 건너뛴다. "DNS만 고장, 라우팅은 정상"이라는 상황에 정확히 들어맞는다.

---

## 왜 다른 우회책보다 나은가

최근에 [Tailscale MagicDNS가 안 켜지는 문제](/dev/2026/08/30/magicdns가-4개월간-안-켜졌다-47바이트짜리-진범/)를 겪었다. 테일넷 라우팅은 정상인데 이름만 안 풀리는 상태였다. 목표는 DNS 디버깅이 아니라 그 서버에 붙는 것이었다.

선택지가 셋이었다.

| 방법 | 결과 |
|---|---|
| `https://<IP>/` 직접 접속 | **실패.** 서버가 리버스 프록시 뒤에 있어 SNI 매칭을 요구했고, SNI가 IP라 TLS alert로 끊김 |
| `curl --resolve name:443:<ip>` | 동작하지만 **curl에만 적용.** Node 프로세스는 여전히 못 붙음 |
| `/etc/hosts` 한 줄 | **curl, Node, 브라우저가 한꺼번에 해결** |

세 번째가 이긴 이유가 두 가지다.

**첫째, 적용 지점이 `getaddrinfo` 하나다.** 프로세스마다 따로 설정할 필요가 없다. curl에는 `--resolve`, Node에는 별도 lookup 훅, 브라우저에는 또 다른 설정을 거는 대신 OS 레벨에서 한 번에 끝난다.

**둘째, 호스트명이 그대로 유지된다.** IP로 직접 접속하면 TLS SNI와 HTTP `Host` 헤더가 IP가 되어버리지만, hosts는 이름을 유지한 채 목적지 IP만 바꾼다. **인증서 검증과 이름 기반 라우팅이 그대로 통과한다.** 리버스 프록시나 CDN 뒤에 있는 서비스를 다룰 때 이 차이가 결정적이다.

---

## 써도 되는 경우

- **DNS 고장 임시 우회** — 위 사례
- **로컬 개발** — `dev.myapp.com`을 `127.0.0.1`로. 쿠키 도메인이나 OAuth 리다이렉트 URI 때문에 `localhost`로는 안 되는 경우에 특히 유용하다
- **DNS 전파 전 리허설** — 새 서버 IP를 hosts에 박고 실제 도메인으로 접속해 검증. 전환 전에 실물 확인이 가능하다
- **차단** — 광고나 트래커 도메인을 `0.0.0.0`으로
- **DNS를 못 건드리는 환경**에서 한두 개 호스트만 고정해야 할 때

## 쓰면 안 되는 경우

**와일드카드가 안 된다.** `*.example.com` 같은 건 표현할 수 없다. 이게 가장 큰 한계다. 내 경우도 서버 하나만 뚫었을 뿐 테일넷 전체가 열린 게 아니었다. 서브도메인 단위로 처리해야 한다면 macOS는 `/etc/resolver/<도메인>` 파일을, 리눅스는 `dnsmasq`나 `systemd-resolved`를 써야 한다.

**포트나 경로는 못 바꾼다.** 이름을 IP에 매핑할 뿐이다. 포트 리다이렉트가 필요하면 프록시나 방화벽 규칙이 답이다.

**인증서는 별개다.** hosts로 이름이 유지되더라도, 그 IP의 서버가 해당 이름의 인증서를 갖고 있지 않으면 그대로 실패한다. hosts는 DNS 응답을 바꿀 뿐 TLS 신뢰 관계에는 관여하지 않는다.

**자체 리졸버를 쓰는 것들은 무시할 수 있다.** Docker 컨테이너는 자기 네임스페이스의 hosts를 본다. 일부 정적 링크 바이너리는 시스템 리졸버를 우회한다. 브라우저의 DoH 설정에 따라서도 달라질 수 있으니, 특정 앱만 안 되면 여기를 의심하자.

**영구 해법으로는 부적합하다.** IP가 바뀌면 **조용히** 깨진다. 이게 가장 고약하다. 에러가 "연결 실패"로만 나오고 이름은 멀쩡히 풀리니, DNS를 의심조차 하지 않게 된다.

## 가장 위험한 부작용: 검증을 막는다

이번에 실제로 겪은 것이라 따로 적어둔다.

Tailscale을 전부 걷어낸 뒤, hosts에 남아 있던 그 줄은 **도달 불가능한 IP를 가리키는 죽은 줄**이 됐다. 그것만으로도 문제지만 더 나쁜 게 있었다.

**만약 지우지 않았다면, 앱을 재설치한 뒤 MagicDNS가 진짜로 고쳐졌는지 확인할 방법이 없었다.**

hosts가 DNS보다 먼저 답을 주기 때문이다. 이름이 풀리는 걸 보고 "고쳐졌다"고 결론 냈을 텐데, 실제로는 hosts가 답한 것이고 DNS 계층은 여전히 죽어 있었을 수 있다. **우회책이 남아 있으면 근본 해결을 검증할 수 없다.**

그래서 작업 순서를 이렇게 못 박았다.

1. 재설치 후 `scutil --dns | grep -c "100.100.100.100"`이 1 이상인지 먼저 확인
2. **그게 통과한 뒤에** hosts 줄 제거
3. hosts 없는 상태에서 이름 해석과 서비스 응답을 다시 검증

일반화하면 이렇다.

> 임시 우회를 걸어둔 채로는 근본 원인이 고쳐졌는지 알 수 없다. **검증은 반드시 우회를 걷어낸 상태에서 한다.**

## macOS 실무

```bash
# 편집 — vifs는 잠금 처리를 해줘서 에디터로 직접 여는 것보다 안전하다
sudo vifs

# 형식: IP<탭/공백>호스트명 [별칭...]   #는 주석
203.0.113.10   staging.example.com   # 2026-08-30 임시, DNS 전환 후 제거

# 수정 후 캐시 플러시
sudo dscacheutil -flushcache && sudo killall -HUP mDNSResponder

# 적용 확인 (hosts를 포함한 시스템 경로로 조회)
dscacheutil -q host -a name staging.example.com
```

몇 가지 알아둘 점.

- **SIP는 `/etc/hosts`를 보호하지 않는다.** root면 그냥 수정된다. 권한은 `-rw-r--r-- root:wheel`이 정상이다.
- **확인은 `dig`가 아니라 `dscacheutil`로 한다.** `dig`는 DNS 서버에 직접 질의하므로 hosts를 아예 보지 않는다. hosts 적용 여부를 `dig`로 확인하려다 헛다리를 짚기 쉽다.
- 기본 파일에는 `localhost`, `broadcasthost`, `::1` 세 줄만 있다. **그보다 많으면 누군가 뭔가를 했다는 뜻이다.**

리눅스라면 `/etc/nsswitch.conf`의 `hosts:` 줄에서 `files`가 `dns`보다 앞에 있는지 확인하면 된다. 기본값은 대개 `files dns`라 hosts가 우선한다.

## 위생 수칙

임시로 넣을 거면 **같은 줄에 주석으로 왜, 언제, 언제 지울지를 남긴다.**

```
203.0.113.10  staging.example.com  # 2026-08-30 DNS 전파 대기용, 09-02 전환 후 삭제
```

`/etc/hosts`는 아무도 정기적으로 들여다보지 않는 파일이다. 반년 뒤 "왜 이 도메인만 이상한 서버로 가지?"를 디버깅하게 되는데, 그때 hosts를 떠올리기까지가 오래 걸린다.

주기적으로 점검하고 싶다면 이 한 줄이면 된다.

```bash
grep -v -E "^\s*#|^\s*$|localhost|broadcasthost" /etc/hosts
```

기본 항목과 주석을 걷어내고 남는 게 있으면 전부 "내가 넣은 것"이다. 각각에 대해 아직 필요한지 물어보자.

## 체크리스트

- [ ] DNS만 고장이고 라우팅은 정상인지 먼저 확인 (아니면 hosts로 안 풀린다)
- [ ] 와일드카드가 필요한지 확인 (필요하면 hosts 말고 리졸버 설정)
- [ ] 넣을 때 주석으로 사유와 삭제 조건 명시
- [ ] 수정 후 캐시 플러시, 확인은 `dscacheutil`로
- [ ] 근본 해결 검증은 **hosts를 지운 상태에서**
- [ ] 정기적으로 비기본 항목 grep으로 점검
