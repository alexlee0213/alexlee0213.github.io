## 결론부터

**`tailscale dns status`가 enabled라고 말해도 macOS 시스템 리졸버에는 아무것도 등록되지 않을 수 있다.** Homebrew로 설치한 오픈소스 `tailscaled`가 macOS DNS를 반쪽만 구성하기 때문이다.

| 확인 지점 | Homebrew판이 하는 일 | 있어야 하는 것 |
|---|---|---|
| `/etc/resolver/` | `search.tailscale` 생성 (검색 도메인만) | 검색 도메인 + 네임서버 |
| 시스템 리졸버 | `100.100.100.100` **미등록** | `100.100.100.100` 등록 |
| `tailscale dns status` | `enabled`라고 보고 | 실제 상태와 일치 |

한 줄 판별식은 이것이다.

```bash
scutil --dns | grep -c "100.100.100.100"
```

**`0`이면 이 맥 어디에도 Tailscale 네임서버가 등록되지 않은 것이다.** 값이 1 이상이어야 MagicDNS가 실제로 동작한다.

## 증상

테일넷의 리눅스 서버 노드에 이름으로 접속이 안 된다. IP로는 멀쩡한데 이름만 안 풀린다.

```
$ curl https://linux-server.tailnet-example.ts.net/health
curl: (6) Could not resolve host: linux-server.tailnet-example.ts.net

$ ping -c 2 100.101.102.103
64 bytes from 100.101.102.103: icmp_seq=0 ttl=64 time=184 ms
64 bytes from 100.101.102.103: icmp_seq=1 ttl=64 time=183 ms
```

라우팅은 살아 있고 이름 해석만 죽었다. 브라우저로도 안 열리고, Node의 `fetch`도 `TypeError: fetch failed`로 떨어진다. 즉 **특정 앱 문제가 아니라 `getaddrinfo` 레벨에서 실패**하고 있다.

## 오진 1: 관리 콘솔만 보고 판단하기

Tailscale 관리 콘솔의 DNS 페이지를 열어보면 MagicDNS가 **켜져 있다**. 네임서버 `100.100.100.100`에 MagicDNS 배지가 붙어 있고, Search Domains에 테일넷 도메인이 들어가 있고, 버튼도 "Disable MagicDNS"로 표시된다. 다 정상이다.

**그런데도 안 된다.** 여기서 배워야 할 것은 이거다.

> 관리 콘솔의 테일넷 전역 설정과, 개별 기기 클라이언트가 그 설정을 시스템에 적용하는 것은 **서로 다른 층**이다.

콘솔은 "이 테일넷은 MagicDNS를 쓴다"고 선언할 뿐이다. 각 노드의 클라이언트가 그 설정을 받아 OS 리졸버에 밀어 넣어야 실제로 이름이 풀린다. **콘솔 스크린샷은 기기 상태의 증거가 아니다.**

---

## 오진 2: 클라이언트에게 물어보기

그럼 클라이언트에게 직접 물어보자.

```
$ tailscale dns status

=== 'Use Tailscale DNS' status ===

Tailscale DNS: enabled.

Tailscale is configured to handle DNS queries on this device.

=== MagicDNS configuration ===

MagicDNS: enabled tailnet-wide (suffix = tailnet-example.ts.net)

Resolvers (in preference order):
  (no resolvers configured, system default will be used)
```

`enabled`라고 한다. 그런데 시스템은 이렇게 말한다.

```bash
$ scutil --dns | grep -c "100.100.100.100"
0
```

**정면으로 모순된다.** 클라이언트는 "내가 DNS를 처리하도록 설정돼 있다"고 믿고, 시스템에는 그 흔적이 없다. 이 모순이 실마리다.

---

## 진짜 원인: 47바이트짜리 파일

`/etc/resolver`를 열어보면 파일이 딱 하나 있다.

```
$ ls -l /etc/resolver/
total 8
-rw-r--r--  1 root  wheel  47  Aug 30 02:03  search.tailscale
```

**47바이트.** 검색 도메인 한 줄 들어가면 끝나는 크기다. 네임서버 지시자가 들어갈 자리가 없다.

`scutil --dns` 출력에서 해당 리졸버 블록을 보면 정확히 그 모양이다.

```
resolver #8
  search domain[0] : tailnet-example.ts.net
  flags            : Request A records
  reach            : 0x00000000 (Not Reachable)
```

**`nameserver[0]` 줄이 아예 없다.** 검색 도메인만 등록됐고 질의를 보낼 대상이 없으니 `reach`가 `Not Reachable`로 뜬다. 껍데기만 꽂힌 것이다.

이 파일을 만든 주체는 Homebrew로 설치한 오픈소스 `tailscaled`였다. 파일 생성 시각과 데몬 기동 시각, 소켓 생성 시각이 전부 일치했다.

```
/etc/resolver/          디렉터리 생성  Jul 26 20:28
/var/run/tailscaled.socket            Jul 26 20:28
root  687  /opt/homebrew/opt/tailscale/bin/tailscaled   26Jul26부터 실행 중
```

## 왜 오픈소스 tailscaled는 반쪽만 하나

macOS의 DNS 설정 경로는 두 가지다.

| 경로 | 방식 | 누가 쓰나 |
|---|---|---|
| `/etc/resolver/<도메인>` 파일 | 도메인별 리졸버를 파일로 선언 | 오픈소스 `tailscaled` |
| `NEDNSSettingsManager` | 네트워크 확장 API로 시스템에 직접 등록 | GUI 앱(App Store판·독립판) |

파일 방식은 root 권한만 있으면 쓸 수 있지만, macOS가 이 파일을 어떻게 해석할지는 필드 구성에 달려 있다. 오픈소스 데몬은 GUI 앱이 쓰는 네트워크 확장 API에 접근할 수 없으므로 파일 방식에 의존하는데, 이 경로에서 네임서버까지 온전히 밀어 넣지 못하는 경우가 생긴다.

정리하면 **터널은 정상, DNS만 반쪽**이라는 어중간한 상태가 만들어진다. 그리고 이 상태가 특히 고약한 이유는 다음과 같다.

- `tailscale status`는 정상이다. 피어도 다 보인다.
- ping도 된다. TCP 연결도 된다.
- IP를 아는 서비스는 전부 정상 동작한다.
- **이름을 쓰는 것만 조용히 실패한다.**

그래서 "DNS 문제"라는 인식에 도달하는 데 시간이 걸린다.

## 판별 커맨드 세트

Tailscale에서 이름이 안 풀릴 때 순서대로 실행하면 원인 위치가 좁혀진다.

```bash
# 1. 시스템 리졸버에 Tailscale 네임서버가 있는가 (0이면 미등록)
scutil --dns | grep -c "100.100.100.100"

# 2. 리졸버 파일이 어떻게 생겼나 (네임서버 줄이 있는지)
ls -l /etc/resolver/
cat /etc/resolver/*

# 3. 시스템 경로로 이름이 풀리는가 (빈 값이면 미적용 확정)
dscacheutil -q host -a name <호스트명>

# 4. Tailscale 리졸버에 직접 물으면 답하는가 (여기서 나오면 리졸버는 살아있음)
dig +short @100.100.100.100 <호스트명>

# 5. 클라이언트는 뭐라고 말하나 (3, 4와 어긋나면 그게 실마리)
tailscale dns status
```

**핵심은 4번과 3번의 대조다.** `dig @100.100.100.100`은 리졸버에 직접 질의하므로 Tailscale 리졸버 자체가 살아 있으면 항상 성공한다. 그런데 `dscacheutil`이 빈 값이면, 리졸버는 멀쩡한데 **시스템이 그 리졸버를 모르는 것**이 확정된다.

## 당장 넘어가야 한다면

원인 규명이 목적이 아니라 오늘 안에 붙어야 한다면 `/etc/hosts` 한 줄이 가장 빠르다.

```bash
# IP는 tailscale status로 확인
sudo vifs
# 100.101.102.103  linux-server.tailnet-example.ts.net  # 임시, MagicDNS 복구시 제거
```

`getaddrinfo`가 hosts를 DNS보다 먼저 보기 때문에 curl, Node, 브라우저가 한꺼번에 해결된다. 호스트명이 유지되므로 TLS SNI 매칭이 필요한 경우에도 안전하다.

다만 이건 반창고다. 지우는 조건을 주석으로 같이 적어두지 않으면 몇 달 뒤 원인 모를 장애의 범인이 된다. 자세한 기준은 [/etc/hosts는 언제 고치는가](/dev/2026/08/30/etc-hosts는-언제-고치는가/)에 따로 정리했다.
