## 결론부터

**3편에서 구축한 에이전트 포워딩을 같은 날 오후에 껐다.**

대신 이렇게 바꿨다. 서버는 GitHub과 아예 말하지 않고, 노트북이 양방향 모두 접속을 건다.

```bash
# shared-server-repo = 그 서버를 가리키는 git remote (등록 방법은 아래 '바뀐 구성'에)

# 결과 회수 — 노트북에서
git pull shared-server-repo main && git push origin main

# 코드 전달 — 노트북에서
git push shared-server-repo main
```

서버에는 자격증명이 없다. 3편과 같다. **그런데 에이전트 소켓도 없다.** 이게 달라진 점이고, 이 글은 왜 그 차이가 결정적인지에 대한 것이다.

---

## 3편이 맞았던 것

먼저 틀리지 않은 부분을 분명히 해둔다. 뒤집힌 건 결론이지 사실관계가 아니다.

- **개인키는 소켓을 건너오지 않는다.** 서명 연산을 위탁할 뿐이라는 설명은 정확하다.
- **`ssh-add -D` 한 번으로 즉시 폐기된다.** 디스크에 키를 두는 방식과 비교한 이 장점도 유효하다.
- **tmux의 죽은 소켓 문제와 고정 경로 해법.** 현상 분석도 해법도 옳다.
- **`ControlMaster` 때문에 설정 변경이 안 먹는 함정.** 오늘 포워딩을 *끌* 때도 똑같이 `ssh -O exit`가 필요했다.

3편은 심지어 「한계와 완화」에 이렇게 써뒀다.

> 서버의 root는 `$SSH_AUTH_SOCK`을 가로채 에이전트에 서명을 요청할 수 있다. 구분이 중요하다 — **키 탈취는 불가능하고, 대리 인증은 가능하다.**

위험을 몰랐던 게 아니다. **적어놓고, 작게 평가했다.** 문제는 거기 있었다.

---

## 빠뜨린 것 1 — 공격자를 root로만 상정했다

3편의 문장을 다시 보자. "서버의 **root는**". 위협의 주체가 관리자 권한을 가진 사람으로 고정돼 있다.

그런데 소켓에 접근하는 데 root는 필요 없다.

```bash
$ ls -ld /tmp/ssh-XXXXXXXX
drwx------ 2 user user 4096 Sep 18 11:43 /tmp/ssh-XXXXXXXX
```

디렉터리가 `0700`이라 **다른 사용자**는 못 들어온다. 맞다. 하지만 `user` 권한으로 도는 프로세스는 전부 자유롭게 들어온다. 그리고 이 서버가 무엇을 하는 기계인지 생각해보면 —

이 머신은 GPU가 달린 ML 작업용이다. 하는 일이 **서드파티 코드를 수시로 설치하고 실행하는 것**이다.

- `pip install`이 실행하는 임의의 `setup.py`
- 논문 저자가 올려둔 모델 repo의 학습 스크립트
- `requirements.txt`가 끌어오는 수백 개의 전이 의존성

이 중 **아무거나 하나**가 `$SSH_AUTH_SOCK`을 읽고 서명을 요청하면 끝난다. 동료의 악의도, 권한 상승도 필요 없다. 타이포스쿼팅된 패키지 하나면 된다. 코드 다섯 줄이면 충분하고, 학습 스크립트 안에서는 눈에 띄지도 않는다.

즉 **진짜 공격자는 사람이 아니라 공급망이었다.** 그리고 이 위협은 "같이 쓰는 사람을 얼마나 믿는가"와 무관하게 존재한다. 혼자 쓰는 서버여도 똑같다.

> 일반화하면 이렇다. **에이전트 포워딩의 위험은 "그 호스트의 관리자를 믿는가"가 아니라 "그 호스트에서 도는 모든 코드를 믿는가"로 물어야 한다.** 빌드 서버, CI 러너, 실험용 GPU 박스는 후자의 답이 구조적으로 "아니오"인 기계들이다.

## 빠뜨린 것 2 — 창의 길이를 재지 않았다

"붙어 있는 동안만"이라는 표현은 위험이 작게 들린다. 얼마나 작은지 재본 적이 없었다.

```bash
$ last -n 6
user  pts/0  10.x.x.x  Fri Sep 18 11:43   still logged in
user  pts/1  tmux(...)  Fri Sep 18 11:44   still logged in
user  pts/3  10.x.x.x  Fri Sep 18 02:15 - 11:43  (09:28)
user  pts/0  10.x.x.x  Fri Sep 18 02:15 - 11:43  (09:28)
```

**연속 9시간 28분.** 그리고 그게 끝나자마자 다시 붙어서 측정 시점에 2시간째였다. "접속해 있는 동안"은 사실상 **깨어 있는 내내**였다.

여기에 아이러니가 하나 있다.

3편의 해법이 무엇이었나. tmux 안의 장수 프로세스가 죽은 소켓을 붙들지 않도록 `~/.ssh/agent.sock`이라는 **고정 경로**를 한 겹 두는 것이었다. 그 설정은 사용성 문제를 정확히 해결한다. 동시에 —

- tmux를 쓰는 이유 자체가 **끊지 않고 오래 붙어 있기 위해서**다. 노출 시간의 총합을 늘리는 방향으로 작동한다.
- 공격자 입장에서도 소켓을 **항상 같은 경로에서** 찾을 수 있게 된다. `/tmp/ssh-*/agent.*`를 훑을 필요조차 없다.

**사용성을 위해 만든 편의가 공격자에게도 그대로 편의였다.** 이런 종류의 대칭성은 보안 설계에서 자주 나타나는데, 3편을 쓸 때는 보이지 않았다.

그리고 결정적으로, 공격자가 그 시간에 **깨어 있을 필요가 없다.** 몇 초마다 소켓을 훑는 루프를 cron이나 user systemd unit에 걸어두면 모든 창을 빠짐없이 잡는다. "내가 접속해 있는 순간에만"이라는 제약은 사람을 상대로는 방어지만, **자동화를 상대로는 방어가 아니다.**

## 빠뜨린 것 3 — 기록이 남지 않는다

3편에는 이 이야기가 아예 없다. 그리고 이게 가장 나쁜 항목이다.

에이전트가 서명을 몇 번 했는지, 누가 요청했는지 **노트북 쪽에 아무 로그도 남지 않는다.** 소켓을 통한 서명은 조용하다.

그래서 이런 질문에 답할 수 없다.

- 오늘 내 키로 서명된 요청이 몇 건인가?
- 내가 `git push`를 친 횟수와 일치하는가?
- 지난 3일간 도용이 있었는가?

**모른다. 알 방법이 없다.** 사고가 났는지조차 판정할 수 없는 통제는, 있어도 없는 것과 비슷하다. 반면 deploy key는 repo 설정에 마지막 사용 시각이 찍히고, GitHub 감사 로그에 어떤 키가 눌렀는지 남는다.

완화책이 없진 않다. 키를 `ssh-add -c`로 등록하면 서명마다 확인 프롬프트가 뜬다. 노출 창을 줄이진 못해도 **도용을 눈에 보이게** 만든다. 다만 macOS에는 askpass 헬퍼가 기본 탑재돼 있지 않아서, 그냥 실행하면 보안이 강화되는 게 아니라 `git push`가 실패하는 상태가 된다. 3편은 하드웨어 키·Secure Enclave를 완화책으로 제시했는데, **셋업 비용을 적지 않은 것**도 빠뜨린 부분이다.

## 빠뜨린 것 4 — 범위를 표에 적어놓고 가중치를 안 줬다

3편의 비교표에는 이 줄이 있었다.

| | 에이전트 포워딩 | deploy key |
|---|---|---|
| 서버에 저장 | **없음** | 개인키 |
| 적용 범위 | 계정 전체 | repo 1개씩 |

"적용 범위: 계정 전체"라고 정확히 써놓고, 결정은 **"서버에 저장" 한 칸만 보고** 내렸다. 바로 위 문단이 이렇다.

> 저장하지 않는 선택지가 있는데 굳이 저장할 이유가 없다.

실제로 그 "계정 전체"가 무엇이었는지 오늘 확인했다. 포워딩되던 키는 조직 private repo에 write 권한을 가진 **계정 키**였다. 서버에 체크아웃돼 있던 repo만 8개였고 그중 6개가 회사 조직 소유였는데, 노출 범위는 그 8개가 아니라 **계정이 write할 수 있는 조직 repo 전부**였다.

정리하면 이렇다.

| | 3편이 본 축 | 실제로 중요했던 축 |
|---|---|---|
| 저장 여부 | ✅ 없음 | 한 축일 뿐 |
| 범위 | (표에만 있음) | **조직 전체 write** |
| 기간 | "붙어 있는 동안" | **하루 9.5시간** |
| 감사 | (누락) | **기록 없음** |

**"자격증명을 저장하지 않는다"는 목표를 달성한 것과, 위험이 작아진 것은 별개였다.** 저장을 피한 대가로 범위를 최대로 열어두고 있었다.

## 같은 전제, 반대 결론

가장 뼈아픈 부분은 이거다. 3편은 이렇게 썼다.

> **무인 작업이 없다는 사실이 결정적이었다.**

이 전제는 옳다. 그런데 이 전제에서 한 걸음 더 갈 수 있었다.

무인 push가 없다 = 모든 push는 **내가 노트북 앞에 있을 때** 일어난다. 그렇다면 —

**서버가 GitHub에 인증할 필요 자체가 없다.**

결과를 회수하는 방향은 서버 → 노트북이다. 그러면 노트북이 당기면 된다. 코드를 보내는 방향도 노트북이 밀면 된다. 양쪽 다 노트북이 접속을 거는 쪽이므로 **서버에는 자격증명도, 에이전트 소켓도, 인증 통로도 필요 없다.**

3편은 "서버가 인증하려면 무엇이 가장 안전한가"를 물었다. **물어야 했던 건 "서버가 인증할 필요가 있는가"였다.** 같은 전제에서 더 나은 결론이 나왔고, 한 칸을 덜 갔던 셈이다.

## 바뀐 구성

### 노트북

```bash
# ~/.ssh/config — 두 별칭 모두에서 제거
Host shared-server
  # ForwardAgent yes   # 비활성: 서드파티 코드 상시 실행 → 소켓 노출
Host shared-server-vpn
  # ForwardAgent yes   # 비활성: 동일 사유

# git 전용 별칭을 따로 둔다 (LocalForward·ForwardAgent 없음)
Host shared-server-git
  HostName shared-server.example.net
  User user
  Port 22
  IdentityFile ~/.ssh/id_server
  IdentitiesOnly yes
```

기존 별칭에 포트 포워딩이 붙어 있다면 **git용 별칭을 분리하는 게 낫다.** 안 그러면 git 명령마다 포트 바인딩 경고가 섞여 나온다.

```bash
# repo마다 remote 등록
git remote add shared-server-repo shared-server-git:/home/user/path/to/repo
```

이름이 둘 나오는데 층이 다르다. **`shared-server-git`은 SSH 별칭**(어디로 어떻게 접속할지)이고, **`shared-server-repo`는 git remote 이름**(그 경로에 붙인 별명)이다. remote 이름은 아무거나 좋지만, **기계 이름을 그대로 물려받는 편이 낫다** — `origin`과 나란히 놓였을 때 어디서 당겨온 것인지 한눈에 보이고, 서버가 늘어나도 같은 규칙으로 확장된다.

검증은 실제 값으로 한다.

```bash
$ ssh -G shared-server-vpn | grep -i '^forwardagent'
forwardagent no
```

### 서버

3편에서 추가했던 `.bashrc` 블록을 제거한다. 링크와 남은 소켓도 정리한다.

```bash
rm -f ~/.ssh/agent.sock
rm -rf /tmp/ssh-*          # 죽은 소켓이 남아 있는 경우
```

> 여담. 정리하다 보니 **이틀 전 세션의 소켓 디렉터리가 그대로 남아 있었다.** 비정상 종료 때 sshd가 unlink를 못 한 흔적이다. 죽은 소켓이라 악용 가치는 없지만, 이런 잔여물이 쌓이고 있다는 건 알아둘 만하다.

그리고 노트북에서 **체크아웃된 브랜치로 직접 push**할 수 있게 한 줄 넣는다.

```bash
git config receive.denyCurrentBranch updateInstead
```

기본값인 `refuse`는 체크아웃된 브랜치로의 push를 거부한다. `updateInstead`는 **작업트리가 깨끗하면 작업트리까지 함께 갱신**해준다. bare repo를 따로 두지 않아도 되는 이유가 이것이다.

## 검증

```bash
# 서버: 에이전트가 정말 없는가
$ echo "[$SSH_AUTH_SOCK]"
[]

$ ls -ld /tmp/ssh-* 2>/dev/null
(없음)

# 서버: GitHub 인증이 실패해야 정상이다
$ ssh -T git@github.com
git@github.com: Permission denied (publickey).
```

**마지막 줄이 이 구성의 성공 신호다.** 3편에서는 같은 출력이 고장 신호였다. 판정 기준이 정확히 뒤집혔고, 이건 나중에 스스로를 헷갈리게 만들 지점이라 메모해둘 가치가 있다.

`updateInstead`는 실제 repo를 건드리기 전에 `/tmp`에 스크래치 저장소를 만들어 확인했다.

```bash
# 서버
mkdir -p /tmp/verify && cd /tmp/verify && git init -q -b main
git config receive.denyCurrentBranch updateInstead
echo before > file.txt && git add -A && git commit -qm init

# 노트북 — 클론 후 수정해서 push
git clone -q shared-server-git:/tmp/verify && cd verify
echo after > file.txt && git commit -qam test
git push shared-server-git:/tmp/verify main
```

```bash
# 서버 — 작업트리까지 갱신됐는지
$ cat file.txt
after
$ git status --porcelain | wc -l
0
```

실제 repo로도 왕복해봤는데, 여기서 하나 배웠다. 노트북의 `origin/main` 참조가 낡아 있으면 `ahead 1`처럼 보인다. **회수 전에 `git fetch origin`을 먼저 돌려야** ahead/behind 판정이 정확하다.

## 무엇을 잃었나

정직하게 적는다. 공짜가 아니다.

**1. 서버에서 바로 push하는 즉시성.** 실험 브랜치를 올려 공유하려면 노트북을 한 번 거쳐야 한다. 한 박자 늦다.

**2. 노트북이 켜져 있어야 한다.** 장시간 학습이 끝나고 무인으로 결과를 밀어올리는 흐름은 불가능하다. 다만 이건 3편에서도 마찬가지였다 — 접속이 끊기면 push가 안 되는 건 동일하다.

**3. 작업트리가 더러우면 push가 거부된다.** `updateInstead`의 조건이다. 서버에서 편집 중이면 커밋하거나 stash해야 한다.

**4. repo마다 remote 등록이 필요하다.** 다만 이건 deploy key보다 훨씬 가볍다. 키 생성도, 웹 UI 방문도 없이 한 줄이다.

바꿔 말하면 **얻은 것은 범위와 감사가능성이고, 내준 것은 즉시성이다.** 무인 작업이 없는 워크플로에서는 싼 교환이라고 판단했다.

---

## 언제 이 결론이 틀리나

이 글을 또 뒤집지 않으려면 조건을 명시해두는 게 낫다.

**무인 push가 필요해지면 이 구성은 부족하다.** 그때는 **machine user**가 답이다. 전용 계정을 만들어 필요한 repo에만 초대하고, 조직 팀에 넣어두면 새 repo가 자동으로 커버된다. repo가 수시로 들락거리는 워크로드에서 deploy key가 실패하는 지점 — 새 repo마다 키 생성·UI 방문·설정 추가 — 을 정확히 해결한다. 대신 유료 좌석과 조직 승인이 따른다.

**deploy key는 repo 목록이 안정적일 때만 쓸 만하다.** 실험 repo가 계속 늘어나는 기계에서는 마찰이 커지고, **마찰이 큰 통제는 결국 지켜지지 않는다.** 언젠가 `ForwardAgent yes`를 다시 켜게 된다. 이 점을 고려하지 않고 "가장 안전한 방식"만 고르면 실패한다.

## 남은 교훈

**1. 위협 모델은 "누가"가 아니라 "무엇이 실행되는가"로 써야 한다.** "관리자를 믿는가"로 물으면 GPU 박스도, CI 러너도, 빌드 서버도 안전해 보인다. "여기서 도는 코드 전부를 믿는가"로 바꾸면 답이 달라진다.

**2. "얼마나 오래"를 숫자로 재라.** "접속해 있는 동안만"은 작게 들리고, "하루 9시간 28분"은 그렇지 않다. 같은 사실인데 판단이 갈린다. **측정하지 않은 위험은 자동으로 작게 느껴진다.**

**3. 표에 적은 항목에는 가중치를 줘라.** "적용 범위: 계정 전체"를 써놓고 결정에 쓰지 않았다. 적어두는 것과 반영하는 것은 다른 일이다.

**4. 사용성을 위한 편의는 공격자에게도 편의다.** 고정 경로 심볼릭 링크가 그랬다. 무언가를 안정적으로 찾기 쉽게 만들면, 찾는 주체를 가리지 않는다.

**5. 한 칸 더 갈 수 있는지 물어라.** "어떻게 하면 안전하게 인증할까"를 묻기 전에 "인증이 필요하긴 한가"를 물어야 했다. 제약(무인 작업 없음)이 곧 기회였는데, 그걸 선택지를 좁히는 데만 썼다.

반나절 만에 뒤집힌 글을 지우지 않고 남겨두는 이유도 비슷하다. **결론보다 결론이 바뀐 과정이 더 쓸모 있을 때가 있다.**
