## 요약

- 유휴 회수 기준은 **CPU 95 퍼센타일 / 네트워크 / 메모리가 7일간 모두 20% 미만**일 때다. **AND 조건이라 하나만 깨면 된다.**
- 시간당 30초짜리 `stress-ng` 버스트를 4개월 돌렸지만, **부하량 계산상 CPU 기준을 통과할 수 없는 설정**이었다.
- 이유 둘: 전체 CPU 기준으로 15%밖에 안 됐고, 부하 구간이 전체의 0.83%라 **95 퍼센타일에 아예 잡히지 않는다.**
- 그럼에도 회수되지 않은 건 **계정이 PayG였기 때문**이다. 유휴 회수는 Always Free에만 적용된다.
- 결론: **A1이면 메모리 20% 점유가 가장 싸고 확실하다.** CPU로 막으려면 버스트가 아니라 **상시 저부하**여야 한다.

한 인스턴스(`instance-XXXXXXXX-XXXX`)에서 4개월간 돌린 방어책을 정리했는데, 결론부터 말하면 **그 조치는 아무 역할도 하지 않았다.** 계정이 프리티어가 아닌 PayG라 회수 정책의 적용 대상이 아니었고, 실효가 없다는 판단에 따라 2026년 8월 27일에 비활성화했다.

실패한 방어책이지만 남겨두는 이유는, **왜 실패했는지가 프리티어 사용자에게 그대로 교훈이 되기 때문**이다.

## 1. 오라클의 공식 회수 기준

Always Free 컴퓨트 인스턴스는 **7일 동안 아래 세 조건이 모두 참**이면 유휴로 간주되어 회수될 수 있다.

| 지표 | 임계값 | 비고 |
|---|---|---|
| CPU 사용률 (95th percentile) | **20% 미만** | |
| 네트워크 사용률 | **20% 미만** | |
| 메모리 사용률 | **20% 미만** | **A1 shape에만 적용** |

> Oracle will deem virtual machine and bare metal compute instances as idle if, during a 7-day period, the following are true: CPU utilization for the 95th percentile is less than 20%; Network utilization is less than 20%; Memory utilization is less than 20% (applies to A1 shapes only).
>
> — [Oracle Docs, Always Free Resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)

### 중요한 두 가지 함의

**1. 조건은 AND 결합이다.** 세 개가 *전부* 참일 때만 회수 대상이다. 따라서 **하나만 확실히 깨면 된다.** 굳이 CPU를 태울 필요가 없다.

**2. CPU 기준은 평균이 아니라 95 퍼센타일이다.** 7일 샘플 중 상위 5%가 20%를 넘어야 방어가 된다. 즉 "가끔 짧게 튀는" 부하는 퍼센타일에 잡히지 않아 **무의미하다.**

두 번째가 이 글의 핵심이고, 내가 4개월 동안 놓치고 있던 부분이다.

## 2. 대상 인스턴스 사양

```
Shape        : VM.Standard.A1.Flex  (Ampere, aarch64 / Neoverse-N1)
OCPU         : 2
Memory       : 8 GB
Network      : 2 Gbps
Region       : us-ashburn-1 (iad)
Created      : 2026-04-29
```

A1 shape이므로 메모리 기준(20%)이 함께 적용된다. 8GB의 20%는 약 1.6GB이므로, **1.6GB 이상을 상시 점유하면 CPU와 무관하게 회수 조건이 깨진다.**

> 참고로 이 사양은 PayG 계정 기준이다. [1편](/dev/2026/08/27/2026년-오라클-클라우드-프리티어-조용히-반토막-났다/)에서 다뤘듯 현재 Always Free의 A1 할당량은 2 OCPU / 12GB이며, 그 경우 기준선은 2.4GB가 된다.

## 3. 실제로 취했던 조치

### 3-1. 채택한 방식 — 시간당 버스트

`ubuntu` 사용자 crontab에 등록했다.

```cron
0 * * * * /usr/bin/stress-ng --cpu 1 --cpu-load 30 --timeout 30s > /dev/null 2>&1
```

- 매시 정각, CPU 워커 1개를 30% 부하로 30초간 실행
- 출력은 전부 버림(`> /dev/null 2>&1`). syslog에는 CRON 실행 기록만 남는다
- 사전 설치: `sudo apt install stress-ng` (Ubuntu 24.04 기준 `/usr/bin/stress-ng`)

### 3-2. 초기에 시도했다 접은 방식 — 매분 실행 + 로그

```cron
#* * * * * /usr/bin/stress-ng --cpu 1 --cpu-load 30 --timeout 10s --metrics-brief >> /var/log/stress.log 2>&1
```

매분 10초씩 실행하고 `--metrics-brief` 결과를 축적하는 방식이었다. 인스턴스 생성 당일에만 돌려보고 주석 처리했다. 매분 실행은 로그가 급격히 불어나고, 검증이 끝나면 불필요하다고 판단해서다.

남은 로그 24줄에 실측치가 있었다. 10초 실행당 `bogo ops 723`, `usr time 3.09s`. **10초 중 3.1초만 CPU를 썼으니 1코어의 약 31%**로, 의도한 `--cpu-load 30`과 일치한다.

이 숫자가 나중에 사후평가의 근거가 된다.

### 3-3. 운영 결과

- 2026-04-29 ~ 2026-08-27, 약 4개월간 시간당 1회로 무중단 동작
- 회수당한 적 없음
- **단 이는 크론잡의 효과가 아니다** (4절)

## 4. 사후평가 — 이 방식은 CPU 기준을 못 넘겼을 가능성이 높다

다른 시스템에 그대로 복사하기 전에 반드시 읽어야 할 부분이다.

### 부하량 계산

| 항목 | 값 |
|---|---|
| 워커 1개 × 30% 부하 | 1코어의 30% = **2코어 전체의 15%** |
| 실행 시간 비중 | 30초 / 3600초 = **0.83%** |

### 두 지점에서 기준에 미달한다

**1. 버스트 중에도 전체 CPU가 15%다.** 임계값 20%에 못 미친다. `--cpu-load 30`은 *코어 1개 기준*이지 인스턴스 전체 기준이 아니다. 2코어 인스턴스에서 워커 1개를 30%로 돌리면 전체로는 15%다.

**2. 부하 구간이 전체 시간의 0.83%에 불과하다.** 95 퍼센타일에 잡히려면 상위 5% 구간에 들어야 하는데, 0.83% ≪ 5%이므로 **퍼센타일 계산에서 그냥 묻힌다.**

두 번째가 더 치명적이다. 설령 버스트 강도를 100%로 올렸어도, 시간당 30초로는 상위 5%를 채울 수 없다. **강도의 문제가 아니라 지속 시간의 문제**였다.

### 그럼 왜 4개월간 회수되지 않았나

> **계정이 프리티어(Always Free)가 아니라 PayG였기 때문이다.**

유휴 회수 정책은 **Always Free 인스턴스에만** 적용된다. PayG 계정에서는 CPU·메모리·네트워크가 아무리 낮아도 회수 대상이 아니다. 이 인스턴스는 **애초에 정책의 적용 범위 밖**에 있었고, 크론잡은 4개월간 아무 역할도 하지 않았다.

따라서 3절의 조치를 "4개월간 검증된 방법"으로 받아들이면 안 된다. **한 번도 시험대에 오른 적이 없는 설정**이며, 부하량 계산상 프리티어였다면 CPU 기준을 통과하지 못했을 것이다.

참고로 이 인스턴스는 OpenClaw 봇 등 상시 프로세스로 메모리를 약 1.8GB(23%) 점유하고 있었다. 가정상 프리티어였다면 **A1의 메모리 기준(20%)이 회수를 막아줬을 수는 있다.** 다만 이는 2026-08-27 시점의 단일 관측값에 근거한 추정이고, 실제로 확인된 사실은 PayG 건 하나뿐이다.

역설적이지만 이게 2편의 결론을 뒷받침한다. **애써 만든 CPU 방어는 무용지물이었고, 그냥 돌아가던 워크로드의 메모리 점유가 진짜 방어선이었을 것이다.**

## 5. 다른 시스템에 적용한다면

### 권장 1순위: 메모리를 잡아라 (A1 한정)

가장 싸고 확실하다. CPU를 태우는 것보다 전력·발열·경합 면에서 유리하다.

- 8GB A1이라면 **1.6GB 이상**, 12GB라면 **2.4GB 이상** 상시 점유
- 실제 워크로드(봇, DB, 캐시 등)가 이미 이만큼 쓰고 있다면 **추가 조치 불필요**
- 없다면 `tmpfs`에 더미 파일을 올리거나 상시 데몬을 하나 띄우는 편이 낫다

확인:

```bash
free -m | awk '/^Mem:/ {printf "used %.1f%%\n", $3/$2*100}'
```

### 권장 2순위: CPU를 쓰려면 "상시 저부하"로

버스트가 아니라 **끊기지 않는 부하**여야 95 퍼센타일을 넘긴다. 전체 코어 기준 20%를 여유 있게 상회하도록 잡는다. 2코어면 워커 2개 × 25% 정도다.

크론이 아니라 systemd 서비스가 맞다.

```bash
sudo tee /etc/systemd/system/keepalive.service >/dev/null <<'EOF'
[Unit]
Description=Idle reclamation keep-alive (CPU)
After=network.target

[Service]
ExecStart=/usr/bin/stress-ng --cpu 2 --cpu-load 25
Nice=19
CPUSchedulingPolicy=idle
Restart=always

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl enable --now keepalive.service
```

`Nice=19` + `CPUSchedulingPolicy=idle`을 주면 실제 작업이 들어올 때 양보하므로 체감 성능 영향이 거의 없다. 다만 스케줄러가 양보하는 만큼 실측 사용률이 떨어질 수 있으니 반드시 검증해야 한다.

### 검증 방법

`sysstat`으로 실제 퍼센타일을 확인한다.

```bash
# 10분간 10초 간격 샘플링 후, 20% 초과 샘플의 비율 확인
sar -u 10 60 | awk '/^[0-9]/ && $NF!="%idle" {u=100-$NF; n++; if(u>20) c++} END {printf "20%% 초과 샘플: %d/%d (%.1f%%)\n", c, n, c/n*100}'
```

이 비율이 **5%를 넉넉히 넘어야** 95 퍼센타일 기준을 통과한다. 내가 처음부터 이걸 돌려봤다면 4개월을 헛돌리지 않았을 것이다.

### 대안 도구

- [`lookbusy`](https://hub.docker.com/r/fogforest/lookbusy) — CPU/메모리를 목표치로 고정 점유. 목적에 더 직관적이다
- `NeverIdle` — 오라클 회수 방지 전용 Go 바이너리. CPU/네트워크/메모리 동시 대응

## 6. 비활성화

PayG로 전환되면 회수 정책 자체가 적용되지 않으므로 제거하면 된다.

```bash
crontab -l > /tmp/crontab.bak   # 백업 먼저
crontab -e                      # 해당 라인 앞에 '#' 추가
```

이 인스턴스에서는 삭제하지 않고 **주석 처리로 보존**했다. 프리티어 시스템에 재사용할 때 주석만 해제하면 되도록 원본 명령줄을 그대로 두었고, `stress-ng` 바이너리도 제거하지 않았다.

## 7. 정리

- 회수 기준은 **CPU 95p / 네트워크 / 메모리가 각 20% 미만으로 7일간 모두 참**일 때. **AND 조건이라 하나만 깨면 된다.**
- A1이면 **메모리 20% 점유가 가장 쉽고 확실한 방어선**이다.
- CPU로 방어하려면 **버스트가 아니라 상시 부하**여야 한다. 시간당 30초 크론잡은 퍼센타일에 잡히지 않는다.
- `--cpu-load`는 **코어 1개 기준**이다. 인스턴스 전체 사용률로 환산해서 계산할 것.
- **PayG 계정에는 이 정책이 적용되지 않는다.** 요금제부터 확인하고 시작하자.
- 설정을 넣었으면 **`sar`로 실측 검증**할 것. 계산 없이 넣은 방어책은 방어책이 아니다.
