## 요약

- ARM과 AMD는 **별개 할당량**이다. 합쳐서 **최대 4대**를 동시에 쓸 수 있다.
- 진짜 제약은 CPU가 아니라 **200GB 블록 스토리지**다. 4대를 만들면 전부 소진된다.
- OCPU 환산이 다르다. **ARM 1 OCPU = 1 vCPU(물리 코어 전용), x86 1 OCPU = 2 vCPU(SMT)**.
- 성능 격차는 CPU 약 16배, RAM 12배, 그리고 **인터넷 대역폭 40배**(50Mbps vs 2Gbps).
- AMD 마이크로의 **50Mbps 제한**은 잘 안 알려져 있는데, 용도를 결정적으로 제약한다.
- **ARM을 메인, AMD를 보조**로 쓰는 게 정답이다.

---

## 1. 둘 다 쓸 수 있다

가장 많이 받는 오해가 "둘 중 하나만 고르는 것"이다. 아니다. 별개 할당량이다.

| | ARM (`VM.Standard.A1.Flex`) | AMD (`VM.Standard.E2.1.Micro`) |
|---|---|---|
| 대수 | 최대 2대 | 최대 2대 |
| CPU | 합쳐서 **2 OCPU** | 대당 **1/8 OCPU** (버스트 가능) |
| RAM | 합쳐서 **12GB** | 대당 **1GB** |
| 배분 | 자유 (Flex) | 고정 |

공식 문서도 두 셰이프를 각각 별도로 명시한다.

> **Micro instances (AMD processor):** All tenancies get up to two Always Free VM instances using the VM.Standard.E2.1.Micro shape.
> **OCI Ampere A1 Compute instances (Arm processor):** ... For Always Free tenancies, this is equivalent to 2 OCPUs and 12 GB of memory.

즉 **ARM 2대 + AMD 2대 = 4대**가 가능하다.

---

## 2. 진짜 제약은 디스크다

CPU 할당량만 보면 4대를 다 만들 수 있을 것 같지만, 실제로 발목을 잡는 건 스토리지다.

- 블록 볼륨 총량: **200GB** (부팅 볼륨 + 블록 볼륨 합산)
- 인스턴스당 최소 부팅 볼륨: **47GB** (기본값 50GB)

> Because the minimum boot volume size allowed for compute instances is 50 GB, launching four instances will use all your Always Free Block Volume resources.

그래서 실질적인 선택지는 이렇게 갈린다.

| 조합 | 디스크 배분 | 성격 |
|---|---|---|
| ARM 1대 몰빵 (2코어/12GB) | 부팅 50GB + 블록 150GB = **200GB 한 대** | 메인 서버 하나를 제대로 |
| ARM 1대 + AMD 2대 | 각 50~66GB | 메인 1 + 보조 2 |
| ARM 2대 + AMD 2대 | 각 50GB | 대수 최대, 디스크는 빠듯 |

**개인 프로젝트라면 첫 번째를 권한다.** 2코어 12GB에 200GB 디스크 한 대가, 잘게 쪼갠 4대보다 거의 항상 유용하다.

---

## 3. OCPU 환산이 다르다 (헷갈리는 지점)

오라클은 CPU를 OCPU라는 자체 단위로 센다. 그런데 아키텍처마다 환산이 다르다.

> 1 OCPU on Arm A1 (Compute) = 1 core on Arm A1 (Compute) or 1 vCPU
> 1 OCPU on x86 (AMD and Intel) = 2 vCPUs

| | 1 OCPU의 의미 |
|---|---|
| ARM A1 (Ampere Altra) | 물리 코어 1개 = **1 vCPU** (SMT 없음) |
| x86 (AMD/Intel) | 물리 코어 1개 = **2 vCPU** (SMT 있음) |

숫자만 보면 ARM이 손해 같지만 **실제로는 반대다.** A1은 코어 하나를 온전히 독점하고 3.0GHz로 일정하게 돈다. 옆 스레드에 성능을 뺏기는 noisy neighbor 현상이 없어 지연이 예측 가능하다.

`lscpu`로 확인하면 `Thread(s) per core: 1`이 나온다. DB처럼 일관된 지연이 중요한 워크로드에 유리한 구조다.

---

## 4. 성능 격차는 "체급이 다르다" 수준

| 항목 | ARM A1.Flex | AMD E2.1.Micro | 배율 |
|---|---|---|---|
| CPU | 2 OCPU (물리 코어 2개 전용) | 1/8 OCPU | **약 16배** |
| RAM | 12GB | 1GB | **12배** |
| **인터넷 대역폭** | OCPU당 1Gbps → **2Gbps** | **50Mbps** | **40배** |
| 내부망 대역폭 | 2Gbps | 480Mbps | 4배 |
| 프로세서 | Ampere Altra Q80-30, 3.0GHz | AMD EPYC 7551 / 7742 / 7J13 |  |
| Windows | ❌ 미지원 | 지원 |  |

### ⭐ 50Mbps 함정

세 번째 줄이 이 글에서 가장 중요한 부분이다. 공식 문서의 AMD 마이크로 설명은 이렇다.

> **Networking:** Includes one VNIC with one public IP address and **up to 50 Mbps network bandwidth via the internet**. Traffic to private IPs ... is up to 480 Mbps.

**공인 IP로 나가는 트래픽이 50Mbps로 제한된다.** 초당 약 6MB다.

이게 의미하는 바:

- 파일 다운로드 서버 ❌
- 미디어 스트리밍 ❌
- 이미지가 많은 사이트 ❌ (동시 접속자가 조금만 늘어도 체감이 확 나빠진다)
- 트래픽 많은 API 서버 ❌

프리티어의 최대 강점이 월 10TB 아웃바운드인데, **AMD 마이크로로는 그 대역폭을 쓸 수가 없다.** 50Mbps를 24시간 꽉 채워도 월 16TB 정도라 이론상 10TB는 채우지만, 실제 서비스에서 50Mbps는 금방 병목이 된다.

### 버스터블이라는 점도 감안하자

AMD 마이크로는 평소 1/8 코어만 보장받고 여유가 있을 때만 잠깐 더 쓴다. 부하가 지속되면 스로틀링이 걸린다. `npm install`이나 `docker build` 같은 작업은 체감상 매우 느리다.

---

## 5. 아키텍처 차이와 호환성

ARM은 **aarch64**, AMD는 **x86_64**다. 명령어 집합이 아예 달라서 x86용 바이너리는 ARM에서 돌지 않는다.

### ✅ 문제없는 것

nginx, Apache, Caddy / PostgreSQL, MySQL, MariaDB, Redis, MongoDB / Node.js, Python, Go, Rust, Java, PHP / Docker, Docker Compose, K3s

주요 공식 Docker 이미지는 대부분 multi-arch로 배포되므로 그냥 돌아간다. 요즘은 예전만큼 문제되지 않는다.

### ⚠️ 막히는 것

- **arm64 빌드가 없는 Docker 이미지** → `exec format error`로 죽는다
- **x86 전용 상용 바이너리** (일부 라이선스 소프트웨어, 레거시 에이전트)
- **Steam 기반 게임 서버** (거의 전부 x86 전용)
- **Windows** — A1 셰이프는 아예 미지원이다

> Windows images are not supported on this shape.

### 우회: qemu 에뮬레이션

```bash
docker run --privileged --rm tonistiigi/binfmt --install all
docker run --platform linux/amd64 <x86-only-image>
```

돌긴 하지만 **3~10배 느려진다.** 임시방편이지 운영용은 아니다. 이럴 때 **AMD 마이크로 1대를 x86 전용 백업으로 남겨두면** 유용하다.

---

## 6. 가용성 차이 — 실전에서 제일 중요할 수도

| | ARM A1 | AMD Micro |
|---|---|---|
| 재고 | **항상 부족.** capacity 에러 빈발 | **거의 항상 여유** |
| AD 우회 | 여러 AD 시도 가능 | ❌ **AD 1곳에서만 생성 가능** |
| 춘천 리전 | ❌ 생성 불가 | 가능 |

> Instances using the VM.Standard.E2.1.Micro shape can only be created in one availability domain.

좋은 건 다들 원하니 ARM은 늘 품절이다. AMD 마이크로는 성능이 약해서 인기가 없는 만큼 바로 잡힌다.

여기서 실전 순서가 나온다. [2편](/dev/2026/08/27/out-of-capacity와-유휴-회수-오라클-프리티어-두-관문-뚫기/)에서도 언급했듯, **AMD 마이크로를 먼저 확보해 발판을 만들고 그 위에서 ARM 확보 스크립트를 돌리는 것**이 가장 실패가 적다.

---

## 7. 그래서 어떻게 쓸까

**ARM을 메인으로 쓰고, AMD는 보조 도구로 포지셔닝한다.**

| 용도 | 적합 |
|---|---|
| 웹서비스, DB, Docker 스택, K3s | **ARM** |
| CI 러너, 빌드 서버 | **ARM** |
| 게임 서버 (마인크래프트 등 JVM 기반) | **ARM** |
| 대역폭을 쓰는 모든 것 | **ARM** (AMD는 50Mbps) |
| ARM 재고 확보 스크립트 상시 구동 | AMD |
| 모니터링 / 헬스체크 / 알림봇 | AMD |
| DNS, 소규모 VPN 종단점 | AMD |
| x86 전용 바이너리 실행 | AMD |

### 유휴 회수 관점의 차이

[2편](/dev/2026/08/27/out-of-capacity와-유휴-회수-오라클-프리티어-두-관문-뚫기/)에서 다룬 유휴 회수 조건에도 차이가 있다.

- **ARM(A1)**: CPU·네트워크·메모리 세 조건 모두 검사 → 메모리 20%(약 2.4GB)만 점유해도 안전
- **AMD 마이크로**: **메모리 조건 미적용**. CPU와 네트워크만 봄

역설적으로 **1GB짜리 AMD 마이크로를 놀리고 있으면 회수 위험이 ARM보다 높다.** 보조 노드로 쓰더라도 뭔가 주기적으로 돌게 해두는 게 좋다.

## 정리

1. ARM과 AMD는 별개 할당량 — **최대 4대**
2. 진짜 병목은 **200GB 디스크**
3. OCPU 환산이 다르다 — ARM은 물리 코어 전용이라 실질 성능이 좋다
4. **AMD 마이크로의 50Mbps 제한**이 용도를 결정적으로 제약한다
5. ARM 메인 + AMD 보조. 단, AMD를 완전히 놀리지는 말 것
